# 标题优化工具 · title-tool

面向 PC 的本地网页工具。上传两张关键词信息截图，结合原标题与用户选定的参考标题，通过火山方舟豆包模型生成 **Item Name（商品标题）** 和 **Item Highlights（商品亮点）**。

前端使用原生 HTML、CSS、JavaScript，无需构建；本机 Python 服务负责读取密钥和调用方舟。当前规则版本：`20261027-1`。

## 1. 启动

需要 Python 3.9 或更新版本，无第三方 Python 依赖。

```bash
git clone https://github.com/cccadyforwork-cloud/title-tool.git
cd title-tool
python3 server.py
```

浏览器访问 **http://127.0.0.1:8011/**。Windows 可使用 `py server.py`。也可双击 `启动工具.command`（macOS）或 `启动工具.bat`（Windows）。

必须使用本项目的 `server.py`；普通静态文件服务器只能展示页面，不能调用模型。服务仅监听本机地址。关闭服务进程后，生成接口也会停止。

## 2. 模型与 API Key

| 配置项 | 当前默认值 / 用途 |
| --- | --- |
| 方舟接口 | `https://ark.cn-beijing.volces.com/api/coding/v3/responses` |
| `ARK_MODEL` | `doubao-seed-2.1-lite`，识图、资料整理和选词 |
| `ARK_GENERATION_MODEL` | `doubao-seed-2.1-pro`，生成文案并在同次响应中自检 |
| `ARK_REVIEW_MODEL` | 兼容旧配置，作为未设置生成模型时的默认来源；当前没有独立复核调用 |
| `ARK_API_KEY` | 由本机服务读取，不发送到前端 |

密钥读取顺序：

1. 当前进程的 `ARK_API_KEY` 环境变量。
2. macOS 钥匙串：服务名 `prompt-tool.api-keys`、账户名 `ARK_API_KEY`，可复用本机 prompt-tool 已保存的密钥。

识图、选词和生成调用均显式关闭深度思考。更新模型配置后须重启已运行的本机服务；工作台内置版使用服务器统一管理的方舟密钥和 `ARK_MODEL`。

其他系统或没有钥匙串记录的设备，需要先设置环境变量。项目不会自动加载 `.env` 文件。

### 在另一台设备同步

Git 会同步源码、模型地址、默认模型、规则和文档，**不会同步真实 API Key**。另一台设备若已有同名环境变量或 prompt-tool 钥匙串记录，可直接启动；否则需要一次性导入密钥。公开仓库中不得保存真实密钥、令牌或包含它们的配置。

浏览器历史记录也不通过 Git 同步，见第 7 节。

## 3. 输入资料

| 输入 | 是否必填 | 含义与要求 |
| --- | --- | --- |
| 竞品流量占比截图 | 是 | 必须能看见明确的“流量占比 / Traffic Share”列，优先指导标题选词 |
| 类目搜索量截图 | 是 | 必须能看见明确的“月搜索量 / Monthly Search Volume”列，优先指导亮点选词 |
| 原有标题 | 是 | 确定当前商品身份、品牌，以及颜色、数量、尺寸、型号等重要变体 |
| 竞品参考标题 | 否 | 用户选定即视为确认适用，其中功能、结构、材质、用途、人群可直接采用 |

- 两张图均支持 JPG、PNG、WebP，每张最大 8 MB，可点击或拖拽上传并预览。
- 截图必须是关键词信息表，不从商品图片猜关键词。
- 两类指标分别读取、排序和保留来源；同词合并后并列展示两个指标，不能把月搜索量换算成流量占比或混算分数。
- 不把购买率、广告 / 自然流量分布、ABA 集中度等其他百分比当作流量占比。
- 遮挡、模糊、横线和空值跳过，不猜测。百分比下方的灰色数量不能拼进百分比。两张表各最多取 20 个词。
- 参考标题的属性不需要在原标题中重复证明，不再检查其对实物的适用性；当前商品身份、品牌和变体仍以原标题为准，不套用竞品品牌或颜色。
- 撰写规则固定在本机服务中，前端没有编辑规则入口；请求中的自定义 `rules` 不参与生成。

## 4. 生成规则

### 总体顺序

**字符限制 → 资料准确 → 相关高价值关键词 → 商品身份与重要变体清楚 → 英文自然。**

商品身份、品牌和重要变体必须保留；所有描述来自原标题或用户选定参考。关键词与具体功能、使用场景要自然结合，不新增未提供的材质、功能、数量、效果或使用人群。

| 字段 | 字符规则 | 关键词规则 | 内容安排 |
| --- | --- | --- | --- |
| Item Name | **68–75 字符** | 至少 3 个互不包含的完整截图词组 | 高流量占比词优先，核心品类词尽量靠前；保留当前身份、品牌与重要变体，必要时用类目词补足独立词组 |
| Item Highlights | **100–125 字符，125 为硬上限** | 至少 3 个互不包含、具有类目搜索量数据的完整词组 | 优先高搜索量词；将关键词与具体功能、结构、使用场景 / 人群连成自然英文 |

**字符数包含空格、标点和连字符，不是英文单词数。** 两个字段分别计数。

亚马逊美国站自2026-07-27起对非媒体类商品实行标题最多75字符（含空格）、Item Highlights最多125字符的新规则，见[官方公告](https://sellercentral.amazon.com/seller-forums/discussions/t/145b6d0f-999c-4555-896c-c694bda2e470?mons_sel_locale=en_US)。68和100是本工具的写作目标下限，不是亚马逊官方最低长度要求。

### 关键词怎样计数

- 忽略大小写，按完整词组边界匹配；语义改写不等于原词组命中。
- 标题和亮点分别核对，不能跨字段拼成词组。
- 包含关系只计一组：`pill cutter` 与 `small pill cutter` 不能算两组。
- 单复数和连字符变体不重复计数，例如 `pill cutter`、`pill cutters`、`pill-cutter`。
- 标题要求的 3 组必须实际出现在标题；亮点要求的 3 组必须实际出现在亮点。
- 两字段可以重复必要关键词。达到最低数量后，尽量增加有价值的自然覆盖，但不能挤掉具体功能与用途。
- 不为凑数使用错拼、其他语言词、生硬查询片段或孤立连接词。

### 亮点怎样结合功能和使用场景

采用 **“关键词＋具体功能＋使用场景 / 人群”** 的组织方式：

1. 先整理参考标题中具体、简短的功能与用途，为这些内容留位置。
2. 再用至少 3 个高搜索量词组形成自然引导，使用 `with`、`for` 等连接。
3. 尽量保留有意义的限定词和简短完整人群组，如 `removable silicone pad`、`built-in storage`、`vitamins, pets & seniors`。
4. 优先删泛化赞词、重复适用范围和可省略修饰，再考虑额外关键词；不得添加 `Reliable`、`Premium`、`Perfect`、`Best` 等无依据赞词。
5. 已在标题表达的大小、适用范围，不应在亮点重复占用空间而挤掉具体卖点。

### 长度规则怎样执行

- 标题68–75字符是生成规则，也是前后端实际计数的硬校验；七项语义自检全通过也不能放行83字符等超长标题。
- 亮点100–125仍是给豆包的生成硬规则，不能把超过125的亮点视为合格的弹性目标；本次不新增亮点本地长度拦截。
- 豆包须在**同次生成**内计数、压缩、重新确认后才返回最终文案。
- 请求附带已测算字符数的关键词组合、功能短句预算和可用草稿，辅助豆包安排空间；不是本地改写已返回的文案。
- 标题不足68或超过75字符时明确显示实际字符数与要求，不展示为成功结果、不保存到历史。前端独立计数，不信任后端的通过标记或模型自报数字。
- 不自动截断、补词或额外调用模型重写；失败后由用户决定是否重新生成。已有历史记录保留，标记为旧规则结果。

### 已验证的切药器例子

**Item Name：74 字符**

> Pill Cutter, Pill Splitters for Small or Large Pills, Tablet Cutter, Clear

**Item Highlights：122 字符**

> Pill cutter, pill splitter and tablet cutter with removable silicone pad and built-in storage for vitamins, pets & seniors

亮点覆盖 `pill cutter`、`pill splitter`、`tablet cutter` 三组搜索词，同时保留可拆硅胶垫、内置收纳和完整用途人群。

## 5. 调用流程

```mermaid
flowchart LR
    A[两张关键词截图＋原标题＋选定参考] --> B[方舟识别流量占比图]
    A --> C[方舟识别类目搜索量图]
    B --> D[本地合并词池并保留两类指标]
    C --> D
    D --> E[方舟整理资料、功能用途与可用关键词]
    E --> F[本地准备词组组合与字符预算]
    F --> G[豆包一次生成标题和亮点，并同次自检]
    G --> H[实际计数校验标题68–75、核对结构和关键词匹配]
    H -->|通过| I[结果展示、复制、浏览器历史记录]
    H -->|失败| J[显示具体原因、不保存、不自动重写]
```

默认成功路径共 **4 次方舟调用**：两次识图、一次整理、一次生成。图中两次识图是两个逻辑步骤，当前代码顺序执行。

- 不另发英文或事实复核请求，不执行自动循环重写。
- 英文自然度、资料一致性、身份、变体、字段分工、指标优先级和冗余，由豆包在生成响应中一并自检。
- 无效 JSON 每个逻辑步骤最多追加一次格式修复；这属于格式修复，不是反复审核文案。
- 网络异常、资料不足、结构或自检不完整会显示具体错误，不以旧结果冒充新生成结果。

## 6. 豆包和本地各负责什么

| 环节 | 豆包 / 方舟负责 | 本地负责 |
| --- | --- | --- |
| 收集资料 | — | 必填项、图片类型和体积、上传预览 |
| 截图识别 | 读取对应表头、英文词组和同一行指标 | 检查表头与数值格式，去重、排序、合并来源 |
| 商品资料与选词 | 整理用户确认事实、重要变体、功能用途，筛选自然英文词组 | 保留可定位引用供展示，保留原标题短变体；引用摘要不是适用性审批 |
| 生成 | 长度硬规则、关键词＋功能＋场景组织、英文表达、忠实使用资料 | 在请求前提供写作预算，不在返回后截断或补词 |
| 同次生成自检 | 自然度、资料一致性、身份、变体、分工、优先级、冗余 | 检查模型自检字段是否完整且通过，不另行语义审核 |
| 输出处理 | — | 前后端硬校验标题68–75字符、展示亮点计数、核对独立词组/变体/结构，仅保存通过结果 |

基本结构检查包括非空、英文首字母大写、无中文、多余空格、孤立连接词、连续重复词或残缺括号。标题不在68–75字符内、词组不足3组、重要变体丢失、命中已排除词组或豆包自检不通过时，不保存结果。

## 7. 展示、复制与记录

- 分别展示 Item Name、Item Highlights 和真实字符数，支持分别复制或带字段名复制全部。
- 关键词摘要分两排，按对应指标从高到低展示：
  - **标题：**命中的关键词＋流量占比。
  - **亮点：**命中的关键词＋月搜索量。
- 缺少对应指标显示“未提供”，不使用另一类指标代替。
- 可展开查看资料引用、词组匹配位置、来源、筛选理由和豆包自检结果。
- 历史记录使用当前浏览器 `localStorage`，最多 10 条，相同双字段结果去重，支持复制和删除。
- 清理浏览器数据或更换设备不会带走这些记录；Git 仅同步项目文件。
- `workflow.html` 提供横向规则与链路导图，可从工作台右上角打开、打印或保存 PDF。

```bash

```

涉及网页或生成流程修改时，在浏览器实际验证截图上传、生成、复制和历史记录。修改规则或链路时同步维护 README、导图和必要测试；修改 `app.js` 时同步更新 HTML 中脚本版本参数。

每次完成已授权改动并验证后，将源码、规则和文档提交到 Git，并推送到当前分支的远端。推送失败保留本地提交并说明原因；不使用强制推送覆盖其他设备的改动。

另一台设备可使用 GitHub Desktop 克隆本仓库。开始修改前先 Fetch / Pull，结束后 Commit / Push，减少多设备同时改同一文件的冲突。

截图实测产物、旧分发 ZIP、系统缓存和本机密钥配置由 `.gitignore` 排除，不属于源码同步内容。
